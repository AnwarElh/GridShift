Versioning & CI

Mettre le projet sous contrôle de version et le pousser sur un dépôt GitHub privé, sans jamais y embarquer les artefacts de build ni les secrets. Puis, en option, brancher le dépôt à Cloudflare pour un déploiement automatique à chaque push.

Le site est déployé, mais le projet n'était pas encore versionné. On l'initialise en Git, on vérifie l'authentification GitHub, puis on crée un dépôt privé et on pousse le premier commit — en s'assurant que node_modules/ et les artefacts n'y entrent pas.

Vérifier l'authentification GitHub

Le CLI gh (2.92) est déjà authentifié sur le compte username, avec le scope repo. On le confirme avant toute opération distante :

gh auth status   # → connecté, compte « username », scope repo

Le .gitignore

Placé à la racine gaming/, il exclut les dépendances, la sortie de build, l'état local de Wrangler, les secrets et les fichiers d'OS/éditeur. C'est lui qui garantit un dépôt propre (0 node_modules).

# dependencies
node_modules/

# build output
dist/
.astro/
.output/

# cloudflare / wrangler local state
.wrangler/

# env & secrets
.env
.env.*
.dev.vars

# os / editor
.DS_Store
*.log
Pourquoi ces exclusions

.dev.vars et .env* contiennent des secrets — ils ne doivent jamais être commités. .wrangler/, dist/, .astro/ et node_modules/ sont régénérables : les versionner alourdit le dépôt et provoque des conflits inutiles.

Initialiser et pousser le dépôt

Le projet n'était pas versionné au départ. On l'initialise sur la branche main, on configure l'identité, on stage tout (le .gitignore filtre), on commite, puis gh repo create crée le dépôt privé, ajoute le remote et pousse — le tout en une commande.

# à la racine gaming/
git init -b main
git config user.name  "…"
git config user.email "…"
git add -A
git commit -m "Initial commit — BlogStarter"
gh repo create blogstarter --private --source=. --remote=origin --push

Déploiement continu (optionnel)

Le déploiement s'est fait manuellement via wrangler deploy. Pour automatiser, on peut connecter le dépôt GitHub à Cloudflare : chaque git push sur main déclenche alors un build et un déploiement du Worker, sans commande manuelle. Deux chemins concrets s'offrent, au choix :

  1. Via le Dashboard Cloudflare (sans code CI)Cloudflare Dashboard → Workers & Pages → « Connect to Git » → autoriser GitHub, choisir username/blogstarter, définir la commande de build (npm run build) et la branche de production (main). Cloudflare rebuild et redéploie à chaque push. Le plus simple : rien à versionner.
  2. Via un workflow GitHub ActionsAjouter un fichier .github/workflows/deploy.yml qui, sur push main, exécute npm ci → npm run build → wrangler deploy (action cloudflare/wrangler-action). Nécessite un CLOUDFLARE_API_TOKEN stocké en secret GitHub (jamais dans le dépôt). Plus de contrôle (tests, étapes conditionnelles) mais un fichier de plus à maintenir.
À garder en tête

Quel que soit le chemin, le déploiement automatique ne rejoue que le build du site. Les opérations one-shot sur les données restent manuelles quand elles changent : migrations d1 migrations apply --remote, chargement du seed.sql, et upload des créatives sur R2 (r2 object put --remote). Elles ne font pas partie du build et ne sont pas déclenchées par un git push.
