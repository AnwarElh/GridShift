SEO & GEO

Être trouvable par Google et citable par les moteurs IA. Tout le SEO on-page est centralisé dans le BaseLayout ; les données structurées décrivent le site et chaque article ; et comme le contenu est dynamique en D1, les fichiers de crawl (sitemap, robots, ads.txt, llms.txt, RSS) sont des endpoints générés à la volée, pas des fichiers statiques.

7.1 — SEO on-page (BaseLayout)

Le <head> vit dans src/layouts/BaseLayout.astro, alimenté par des props (title, description, canonical, image, type, noindex, articlePublished/Modified, author). Chaque page passe ses valeurs ; le layout produit un head cohérent et complet :

<title>{title}</title>
<meta name="description" content={description} />
<link rel="canonical" href={canonicalUrl} />
{noindex && <meta name="robots" content="noindex, nofollow" />}
<!-- Open Graph -->
<meta property="og:type" content={type} />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:url" content={canonicalUrl} />
<meta property="og:site_name" content="BlogStarter" />
{ogImage && <meta property="og:image" content={ogImage} />}
<meta name="twitter:card" content={ogImage ? 'summary_large_image' : 'summary'} />
{type === 'article' && articlePublished && <meta property="article:published_time" content={articlePublished} />}
{type === 'article' && articleModified && <meta property="article:modified_time" content={articleModified} />}
{type === 'article' && author && <meta property="article:author" content={author} />}
<meta name="theme-color" content="#07080b" />

Points à noter : la canonical est calculée par défaut depuis l'URL courante (new URL(Astro.url.pathname, Astro.site).href) mais peut être surchargée par article ; l'og:image est résolue en URL absolue ; la twitter:card bascule automatiquement en summary_large_image dès qu'une image existe ; noindex (piloté par le champ draft/noindex de l'article) injecte la balise robots. Le theme-color reprend le dark signature #07080b du Command HUD.

Les valeurs viennent de l'article. Sur la page single, elles sont câblées ainsi :

<BaseLayout
  title={`${a.title} — BlogStarter`}
  description={a.meta_description || a.dek}
  image={a.og_image || a.cover}
  type="article"
  noindex={!!a.noindex}
  articlePublished={a.published_at}
  articleModified={a.updated_at || a.published_at}
  author={a.authorName || 'Alex'}>

7.2 — Données structurées (JSON-LD)

Au niveau du site

Le BaseLayout émet sur toutes les pages un @graph décrivant l'Organization et le WebSite (avec une SearchAction pour la sitelinks searchbox) :

const siteJsonLd = {
  '@context': 'https://schema.org',
  '@graph': [
    { '@type': 'Organization', '@id': `${siteHref}#org`, name: 'BlogStarter', url: siteHref,
      logo: { '@type': 'ImageObject', url: `${siteHref}logo.svg`, width: 512, height: 512 } },
    { '@type': 'WebSite', '@id': `${siteHref}#website`,
      name: 'BlogStarter', url: siteHref,
      publisher: { '@id': `${siteHref}#org` },
      inLanguage: 'en',
      potentialAction: {
        '@type': 'SearchAction',
        target: `${siteHref}search?q={search_term_string}`,
        'query-input': 'required name=search_term_string',
      },
    },
  ],
};

Au niveau de l'article

La page single ajoute son propre @graph : un nœud Article — ou Review quand la catégorie est reviews, avec reviewRating et itemReviewed (VideoGame) — plus un BreadcrumbList à trois niveaux (Home → Catégorie → Titre). Le basculement Article/Review et le rating conditionnel :

const jsonld = {
  '@context': 'https://schema.org',
  '@graph': [
    {
      '@type': isReview ? 'Review' : 'Article',
      headline: a.title,
      description: a.dek,
      image: imgAbs,   // repli sur ${siteHref}logo.svg si l'article n'a pas de cover
      datePublished: a.published_at,
      dateModified: a.updated_at || a.published_at,
      author: authorNode,   // { '@type':'Person', name, sameAs?:[twitter] }
      publisher: { '@id': `${siteHref}#org` },   // référence l'Organization (avec logo)
      mainEntityOfPage: pageUrl,
      ...(isReview && a.rating
        ? { reviewRating: { '@type': 'Rating', ratingValue: String(a.rating), bestRating: '10', worstRating: '1' },
            itemReviewed: { '@type': 'VideoGame', name: a.gameName, image: imgAbs } }
        : {}),
    },
    {
      '@type': 'BreadcrumbList',
      itemListElement: [
        { '@type': 'ListItem', position: 1, name: 'Home', item: new URL('/', Astro.site).href },
        { '@type': 'ListItem', position: 2, name: a.catName, item: new URL(`/${a.catSlug}`, Astro.site).href },
        { '@type': 'ListItem', position: 3, name: a.title, item: pageUrl },
      ],
    },
  ],
};

Il est injecté dans le head via le slot dédié du layout :

<div slot="head" set:html={`<script type="application/ld+json">${JSON.stringify(jsonld)}</script>`} />
Pourquoi Review + VideoGame

Marquer une review avec reviewRating (note /10) et itemReviewed de type VideoGame rend l'avis éligible aux rich results « étoiles » et donne un signal net aux moteurs IA sur ce qui est noté. C'est le pendant structuré du bloc verdict visible côté lecteur.

7.3 — Fichiers de crawl & distribution (endpoints dynamiques)

Pourquoi des endpoints custom

Le contenu n'est pas des fichiers Markdown compilés au build : il est en D1 et lu au runtime. Un plugin de sitemap statique (type @astrojs/sitemap) ne le verrait pas. On génère donc chaque fichier de crawl comme un endpoint qui interroge D1 à la volée et renvoie du texte/XML avec le bon Content-Type et un cache s-maxage=3600.

sitemap.xml.ts

Liste la home, les 4 catégories, et tous les articles publiés (30 au moment de la rédaction, mais le nombre est dynamique : WHERE draft=0). Le lastmod n'est posé que sur les articles (updated_at, fallback published_at) ; la home et les catégories sont listées sans lastmod :

const { results } = await DB.prepare(
  `SELECT a.slug, a.updated_at, a.published_at, c.slug AS catSlug
   FROM articles a JOIN categories c ON c.id=a.category_id WHERE a.draft=0`
).all();
const urls = [{ loc: site }];
for (const c of CATEGORIES) urls.push({ loc: `${site}${c}` });
for (const r of results) urls.push({ loc: `${site}${r.catSlug}/${r.slug}`, lastmod: r.updated_at || r.published_at });

robots.txt.ts — crawlers IA bienvenus (GEO)

Autorise tout, déclare explicitement les crawlers IA (GPTBot, PerplexityBot, ClaudeBot) et pointe le sitemap :

const body = [
  'User-agent: *', 'Allow: /', '',
  '# AI crawlers welcome (GEO)',
  'User-agent: GPTBot', 'Allow: /',
  'User-agent: PerplexityBot', 'Allow: /',
  'User-agent: ClaudeBot', 'Allow: /',
  '', `Sitemap: ${site}sitemap.xml`,
].join('\n');

llms.txt.ts — le plan GEO

Pièce maîtresse « Generative Engine Optimization » : un plan Markdown lisible par les IA, avec une description du site puis les articles groupés par catégorie (titre + dek + URL) — de quoi être cité correctement par ChatGPT/Perplexity :

const lines = ['# BlogStarter', '',
  '> Guides, news and reviews for live-service games. Hands-on expertise from real players — we play, we test.', ''];
for (const cat of CATEGORIES) {
  const { results } = await DB.prepare(
    `SELECT a.slug, a.title, a.dek, c.name AS catName FROM articles a JOIN categories c ON c.id=a.category_id
     WHERE c.slug=? AND a.draft=0 ORDER BY a.published_at DESC`).bind(cat).all();
  if (!results.length) continue;
  lines.push(`## ${results[0].catName}`);
  for (const r of results) lines.push(`- [${r.title}](${site}${cat}/${r.slug})${r.dek ? `: ${r.dek}` : ''}`);
  lines.push('');
}

ads.txt.ts & rss.xml.ts

ads.txt est un endpoint placeholder (AdSense requiert ce fichier ; la vraie ligne google.com, pub-…, DIRECT, … sera collée une fois le compte approuvé — voir Partie 08). Le rss.xml sert les 30 derniers articles, avec échappement XML et pubDate RFC-822 :

const { results } = await DB.prepare(
  `SELECT a.slug, a.title, a.dek, a.published_at, c.slug AS catSlug
   FROM articles a JOIN categories c ON c.id=a.category_id
   WHERE a.draft=0 ORDER BY a.published_at DESC, a.id DESC LIMIT 30`).all();

7.4 — Performance & Core Web Vitals

La perf est un pilier du modèle (« vitesse = marge par visiteur »). Les leviers réellement en place :

  • Images dimensionnées : les créatives ont width/height explicites (ex. width="728" height="90") → réservation d'espace, zéro CLS. Les visuels non critiques sont en loading="lazy".
  • imageService passthrough : pas de couche de transformation d'image côté Cloudflare — on sert directement des WebP optimisés (covers en statique, créatives depuis R2).
  • Cache edge : chaque page HTML et chaque endpoint pose un Cache-Control (s-maxage=300 pour les pages, 3600 pour les fichiers de crawl ; immutable 1 an pour les médias R2).
  • JS minimal : seule la page article embarque un petit script inline (barre de progression, scrollspy du sommaire, ancre pub) ; le reste est du HTML rendu au serveur.
  • Polices : Chakra Petch / Inter / JetBrains Mono chargées via Google Fonts, à self-hoster ensuite (prévu, commenté dans le head : « à self-host plus tard »).

7.5 — État SEO/GEO : câblé & reste à faire

Après l'audit, une passe d'amélioration (« Lot C ») a câblé plusieurs leviers directement dans le projet Astro. Voici l'état réel aligné sur le code actuel.

✅ Câblé (post-audit, en production)

  • JSON-LD enrichi : l'Organization porte un logo (ImageObject 512×512, /logo.svg) — requis pour l'éligibilité Rich Results ; l'article référence le publisher par @id, l'image a un repli sur le logo, l'author émet un sameAs (Twitter) quand il existe, et itemReviewed (VideoGame) porte une image.
  • Pages catégories paginées : canonical auto-référente (incluant ?page=N) et noindex au-delà de la page 1 (noindex={page > 1}) — évite le duplicate et la dilution du crawl.
  • X-Robots-Tag: noindex posé sur les endpoints texte ads.txt et llms.txt (fichiers utilitaires non indexables).
  • IndexNow — socle en place : la clé est publiée à la racine (/a1b2…f90.txt) et un helper submitToIndexNow(urls) (src/lib/indexnow.ts) POST vers l'API. Le ping automatique reste à brancher sur un flux de publication (pas d'admin dynamique pour l'instant).

⏳ Reste à faire

  • Ping IndexNow à la publication : appeler le helper depuis le futur flux d'admin/import à chaque nouvel article ou mise à jour.
  • Page auteur + author.url : le sameAs est là, mais il manque une page auteur dédiée (/author/<slug>) à référencer dans author.url pour compléter l'entité E-E-A-T.
  • Crawlers IA à étoffer : ajouter OAI-SearchBot (recherche ChatGPT, distinct de GPTBot) et Google-Extended (opt-in Gemini / AI Overviews) au robots.txt.
  • Politique trailing-slash : figer explicitement la forme canonique des URLs (avec/sans / final).
  • hreflang : non requis (site mono-langue EN) — noté pour lever l'ambiguïté.

GEO — leviers continus (éditorial)

  • Passages citables : structurer chaque section avec une réponse directe en tête (phrase auto-portante), avant le développement — c'est ce qu'un moteur IA extrait et cite.
  • Format llms.txt justifié : suit la spec llmstxt.org (H1, blockquote de résumé, liens groupés), pensé pour être lu/cité par les LLM.
  • Mention de marque off-site : la citation par les IA dépend fortement des mentions hors site (Reddit, YouTube, Wikipedia…). Hors périmètre technique, mais clé — à piloter côté contenu/communauté.
Priorité GEO vs SEO

Le SEO technique est désormais quasi complet côté code. Les leviers GEO (passages citables, E-E-A-T, mentions off-site) sont continus et dépendent surtout de la qualité éditoriale — c'est là que se joue la citabilité IA, pas dans le balisage seul.

Le site est désormais indexable, structuré et citable. Reste à documenter comment il gagne de l'argent tout en restant conforme : c'est la Partie 08.
