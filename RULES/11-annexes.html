Annexes

Les références rapides du projet : la checklist récapitulative du process dans l'ordre, la liste des pièges réellement rencontrés avec leur correctif, et un aide-mémoire des commandes accompagné de l'arborescence du dépôt.

A · Checklist récapitulative

Le process complet, dans l'ordre exact où il a été suivi — du cadrage au déploiement. Chaque étape suppose la précédente validée.

  1. Cadrage éditorialNiche (guides jeux live-service, modèle Prydwen), marque BlogStarter, domaine .com, 4 catégories : Guides · News · Reviews · Setup.
  2. Design system — d'abord, toujoursV2 « Command HUD » (dark, accent volt unique, formes angulaires). Tokens + composants + styleguide navigable, à valider avant la suite. C'est la source de vérité unique.
  3. Gabarits, dans l'ordreArticle → Listing → Home, chacun assemblé à partir des composants du DS (aucun style hors DS).
  4. Modèle de contenu1 Markdown par article + frontmatter YAML, images en convention WordPress wp-content/uploads/AAAA/MM/JJ/, toujours optimisées + métadonnées nettoyées.
  5. Production par agentsUn rédacteur expert par catégorie + un photo-finder. 10 jeux × 3 catégories = 30 articles de test.
  6. Adaptation AstroScaffold + adapter Cloudflare, DS copié et componentisé, couche D1 (Drizzle + migrations), import du contenu → seed, routes SSR + cache edge, médias sur R2.
  7. SEO / GEOhead complet + JSON-LD, endpoints dynamiques (sitemap, robots, ads.txt, llms.txt, rss), perf/CWV.
  8. Monétisation & conformitéEmplacements pub réservés dès le DS (bon CLS), créatives WebP sur R2, bandeau cookies + pages légales.
  9. Déploiement Cloudflarelogin → imageService:'passthrough' (évite le binding IMAGES) → D1/KV/R2 distants → migrations + seed --remote → upload créatives → build → deploy. Vérifs prod à 200.
  10. Versioning & CI.gitignore propre, dépôt privé GitHub (username/blogstarter), déploiement continu optionnel.

B · Pièges à éviter

Les obstacles réellement rencontrés pendant le build, chacun avec son correctif.

1 · Design system générique

La V1 était trop « SaaS sombre générique » (coins arrondis, violet+cyan safe) et a été rejetée. Correctif : refonte en V2 avec un parti pris fort et assumé (« Command HUD » : dark quasi-noir, accent volt unique, formes angulaires).

2 · Astro.locals.runtime.env supprimé

Astro.locals.runtime.env n'existe plus (comportement Astro v6) → erreur 500 au premier run. Correctif : import { env } from 'cloudflare:workers' puis const DB = env.DB, dans chaque page et endpoint qui accède aux bindings.

3 · Agents .claude non reconnus en session

Les agents personnalisés de .claude/agents/ ne sont pas reconnus en cours de session (le registre est chargé au démarrage). Correctif : lancer des agents general-purpose avec le même prompt expert. Ils redeviennent disponibles à la session suivante.

4 · sips laisse un bloc « Photoshop 3.0 »

sips redimensionne mais laisse un bloc « Photoshop 3.0 » (et parfois du XMP). Correctif : utiliser cwebp (strip total des métadonnées) pour les créatives ; pour un JPEG propre, la chaîne cwebp → dwebp → sips. Vérif : strings fichier | grep -iE "xmp|c2pa|openai|adobe|FBMD".

5 · Prompt interactif R2

wrangler r2 bucket create peut poser un prompt interactif (« add on your behalf? ») non confirmé en contexte non-interactif. Correctif : vérifier l'existence du bucket après coup avec wrangler r2 bucket list.

6 · imageService passthrough + KV SESSION

Au deploy, l'adapter réclame un binding IMAGES si le service d'images est actif, et un KV SESSION pour les sessions. Correctif : régler imageService:'passthrough' (évite le binding IMAGES) et provisionner le namespace KV lié à SESSION.

7 · Redémarrage du dev après binding

Un binding ajouté (ex. R2) n'est pas pris en compte par le serveur de dev déjà lancé. Correctif : redémarrer astro dev après tout ajout de binding pour qu'il soit chargé via platformProxy.

8 · Featured = titre seul

Le spotlight « à la une » de la home affichait trop d'éléments. Correctif (choix éditorial validé) : ne garder que le titre pour le featured.

9 · Un sous-agent ne pilote pas d'autres sous-agents

Lors de la production par agents, un sous-agent lancé ne peut pas lui-même orchestrer d'autres sous-agents (pas de fan-out imbriqué). Correctif : le main loop reste le chef d'orchestre — c'est lui qui lance les rédacteurs et le photo-finder en parallèle, collecte leurs résultats et enchaîne. Les sous-agents restent des exécutants à tâche unique.

C · Commandes & arborescence

Aide-mémoire wrangler

npx wrangler login                                         # auth interactive
npx wrangler whoami                                        # compte actif
npx wrangler d1 create blogstarter-db                          # crée la D1 → database_id
npx wrangler kv namespace create SESSION                   # crée le namespace KV
npx wrangler kv namespace list                             # récupère l'id existant
npx wrangler r2 bucket create blogstarter-media                 # crée le bucket
npx wrangler r2 bucket list                                # vérifie le bucket
npx wrangler d1 migrations apply blogstarter-db --remote        # migrations distantes
npx wrangler d1 execute blogstarter-db --remote --file=./seed.sql
npx wrangler r2 object put blogstarter-media/ads/arknights-endfield-728x90.webp --file=media-src/ads/arknights-endfield-728x90.webp --remote
npm run build                                              # build SSR Cloudflare
npx wrangler deploy                                        # déploie le Worker

Aide-mémoire gh & git

gh auth status                                             # compte username, scope repo
git init -b main
git config user.name "…" && git config user.email "…"
git add -A && git commit -m "Initial commit — BlogStarter"
gh repo create blogstarter --private --source=. --remote=origin --push
