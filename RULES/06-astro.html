Adaptation pour Astro

Le HTML validé du design system devient une application Astro rendue côté serveur sur Cloudflare Workers : bindings D1/R2/KV, schéma Drizzle, import du contenu Markdown vers D1, routes SSR avec cache edge, médias servis depuis R2. C'est la partie la plus technique — et celle qui recèle le piège Astro/Cloudflare le plus coûteux.

6.1 — Scaffold du projet

On part d'un projet Astro minimal en TypeScript strict, dans le dossier site/ à côté de design/ et contents/. Les commandes réellement exécutées, dans l'ordre :

# Scaffold Astro minimal, TypeScript strict, sans git, install auto
npm create astro@latest site -- --template minimal --typescript strict --no-git --install --skip-houston --yes
# Adapter Cloudflare (SSR sur Workers)
npx astro add cloudflare --yes
# ORM + outils d'import de contenu
npm install drizzle-orm
npm install -D drizzle-kit gray-matter marked

Versions réelles : Astro ^7.2.6, @astrojs/cloudflare ^14.2.4, drizzle-orm ^0.45, drizzle-kit ^0.31, plus gray-matter (parse le frontmatter YAML) et marked (Markdown → HTML). Node 24, npm 11, wrangler ^4.125.

astro.config.mjs

La config déclare le site canonique, le rendu serveur, et l'adapter Cloudflare. Deux réglages sont déterminants : platformProxy (expose les bindings Cloudflare en dev local via wrangler) et imageService: 'passthrough' (aucun traitement d'image par Cloudflare Images — on sert des <img> statiques et R2).

export default defineConfig({
  site: 'https://votreblog.com',
  output: 'server',
  adapter: cloudflare({
    // Expose les bindings Cloudflare (D1, etc.) en dev local via wrangler
    platformProxy: { enabled: true },
    // Pas de traitement d'image via Cloudflare Images (on sert des <img> statiques / R2)
    imageService: 'passthrough',
  }),
  image: {
    remotePatterns: [{ protocol: 'https' }],
  },
});
Pourquoi passthrough

Sans imageService: 'passthrough', l'adapter cherche à brancher le binding Cloudflare Images au moment du deploy, ce qui échoue si le service n'est pas activé. On sert nos propres images (covers en statique, créatives depuis R2), donc on désactive proprement ce pipeline.

wrangler.jsonc — les bindings

Le worker s'appelle blogstarter. Son point d'entrée est fourni par l'adapter (@astrojs/cloudflare/entrypoints/server). Quatre bindings sont déclarés : ASSETS (le dist/ statique), DB (D1), MEDIA (R2), SESSION (KV pour les sessions Astro).

{
  "compatibility_date": "2026-08-25",
  "compatibility_flags": ["global_fetch_strictly_public"],
  "name": "blogstarter",
  "main": "@astrojs/cloudflare/entrypoints/server",
  "assets": { "directory": "./dist", "binding": "ASSETS" },
  "observability": { "enabled": true },
  "d1_databases": [
    { "binding": "DB", "database_name": "blogstarter-db",
      "database_id": "",
      "migrations_dir": "migrations" }
  ],
  "r2_buckets": [ { "binding": "MEDIA", "bucket_name": "blogstarter-media" } ],
  "kv_namespaces": [ { "binding": "SESSION", "id": "" } ]
}

6.2 — Componentiser le design system

Règle d'or maintenue depuis la partie 02 : le design system reste la source de vérité unique. Concrètement, styles-v2.css est copié tel quel depuis design/ vers site/src/styles/styles-v2.css, puis importé une seule fois, dans BaseLayout.astro :

---
import '../styles/styles-v2.css';
import Header from '../components/Header.astro';
import Footer from '../components/Footer.astro';
---

Les maquettes HTML validées deviennent des composants .astro qui réutilisent les mêmes classes du DS — rendu fidèle, zéro style ad-hoc. Le Header reprend le logo SVG et la nav 4 catégories ; l'ArticleCard reprend .card/.thumb/.body et calcule sa métadonnée droite selon la catégorie :

if (art.catSlug === 'news') right = fmtDate(art.published_at);
else if (art.catSlug === 'reviews') right = art.rating ? `${art.rating}/10` : 'REVIEW';
else if (art.catSlug === 'guides') right = art.tier ? `TIER ${art.tier}` : 'GUIDE';
else right = fmtDate(art.published_at);   // setup (et tout autre) → date

La branche else couvre la catégorie setup (hardware) : elle a bien été créée dans le modèle, mais sans article de test à ce stade — le hardware est en réserve. Faute de tier/rating, une carte setup affiche simplement sa date.

Le DS s'enrichit, dans les deux sens

L'adaptation a révélé des besoins réels (images, grilles, pubs remplies) : on a ajouté au CSS des règles <img> concrètes (.card .thumb img, img.bg), l'utilitaire .grid.cols-N, .ad-slot.filled, .ad-band, .article-hero-split + .ad-square, .article-summary, .flow, .related-grid, .listing-layout/.listing-grid/.listing-side, .ad-anchor. Chaque ajout est mirroré dans design/styles-v2.css pour garder la source de vérité intacte.

6.3 — Couche données D1

Le contenu vit dans D1 (SQLite à l'edge). Le schéma est décrit en TypeScript avec Drizzle (drizzle-orm/sqlite-core) dans src/db/schema.ts. Tables : categories, games, authors, articles, tags, article_tags. La table articles porte le contenu, l'éditorial (rating/verdict/pros/cons/tier) et les champs SEO :

export const articles = sqliteTable('articles', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  slug: text('slug').notNull(),
  title: text('title').notNull(),
  dek: text('dek'),
  bodyMd: text('body_md'),
  bodyHtml: text('body_html'),
  categoryId: integer('category_id').notNull().references(() => categories.id),
  gameId: integer('game_id').references(() => games.id),
  authorId: integer('author_id').references(() => authors.id),
  rating: text('rating'),        // stocké en texte pour préserver "8.2"
  verdict: text('verdict'),
  pros: text('pros'),            // JSON array
  cons: text('cons'),            // JSON array
  tier: text('tier'),
  publishedAt: text('published_at'),
  updatedAt: text('updated_at'),
  featured: integer('featured', { mode: 'boolean' }).default(false),
  // SEO
  metaDescription: text('meta_description'),
  ogImage: text('og_image'),
  canonical: text('canonical'),
  noindex: integer('noindex', { mode: 'boolean' }).default(false),
  draft: integer('draft', { mode: 'boolean' }).default(false),
  // … extrait partiel — la table porte aussi cover, cover_alt, cover_source, reading_time, views
}, (t) => ({
  catSlug: uniqueIndex('idx_articles_cat_slug').on(t.categoryId, t.slug),
  byCategory: index('idx_articles_category').on(t.categoryId),
  byPublished: index('idx_articles_published').on(t.publishedAt),
}));

L'extrait ci-dessus est partiel : la table articles porte aussi les colonnes de cover (cover, cover_alt, cover_source), le reading_time et le compteur views (voir le commentaire dans le code).

Deux détails révélateurs : rating est un texte (pour préserver « 8.2 » sans dérive de flottant) ; l'index unique (category_id, slug) garantit qu'une catégorie ne peut pas avoir deux articles au même slug — ce qui autorise des slugs identiques entre catégories.

Le drizzle.config.ts pointe le schéma en dialecte SQLite :

export default defineConfig({
  dialect: 'sqlite',
  schema: './src/db/schema.ts',
  out: './migrations',
});

On génère la migration puis on l'applique en local :

# Génère migrations/0000_*.sql à partir du schéma Drizzle
npx drizzle-kit generate
# Applique la migration à la D1 locale (via platformProxy)
npx wrangler d1 migrations apply blogstarter-db --local

Les requêtes — src/lib/queries.ts

Toutes les lectures passent par des prepared statements D1 (.prepare(...).bind(...)). Un jeu de colonnes partagé (ARTICLE_CARD_COLS) sert les cartes ; les fonctions couvrent chaque écran : getCategory, listByCategory, latest, latestInCategory, trending, listGames, getArticle, relatedArticles. Exemple, le listing d'une catégorie (articles publiés uniquement, triés par date) :

export async function listByCategory(DB, slug, limit = 24, offset = 0) {
  const { results } = await DB.prepare(
    `SELECT ${ARTICLE_CARD_COLS} FROM articles a JOIN categories c ON c.id=a.category_id
     WHERE c.slug=? AND a.draft=0 ORDER BY a.published_at DESC, a.id DESC LIMIT ? OFFSET ?`
  ).bind(slug, limit, offset).all();
  return results;
}

Les utilitaires (src/lib/util.ts) complètent : badgeClass (mappe la catégorie sur une classe de badge), fmtDate, parseJsonArray (relit les pros/cons JSON) et surtout withHeadingIds, qui injecte des id sur les <h2>/<h3> et construit le sommaire de l'article à la volée :

export function withHeadingIds(html) {
  const toc = [];
  const out = html.replace(/<h([23])>([\s\S]*?)<\/h\1>/g, (_m, lvl, inner) => {
    const text = inner.replace(/<[^>]+>/g, '').trim();
    const id = slugifyHeading(text) || 't' + toc.length;
    if (lvl === '2') toc.push({ id, text });
    return `<h${lvl} id="${id}">${inner}</h${lvl}>`;
  });
  return { html: out, toc };
}
Piège majeur — Astro.locals.runtime.env supprimé

Il s'agit d'un comportement d'API introduit en Astro v6+ (retrait de l'accès à l'env via le runtime), présent sur l'Astro 7.2.6 installé ici : l'ancien accès Astro.locals.runtime.env a été supprimé. Résultat : erreur 500 au tout premier run. Le correctif appliqué partout — pages ET endpoints — est d'importer l'env directement depuis le runtime Workers :

import { env } from 'cloudflare:workers';

const DB = (env as any).DB as D1Database;   // au lieu de Astro.locals.runtime.env.DB

Ce même import sert pour tous les bindings : env.DB (D1), env.MEDIA (R2). On le retrouve en tête de chaque page de données et de chaque endpoint.

6.4 — Import du contenu → D1

Le script scripts/import-content.mjs transforme les 30 fichiers Markdown en un seed.sql prêt à charger. Étapes :

  1. Lire chaque .mdgray-matter sépare le frontmatter YAML (title, dek, cover, rating, tier, tags…) du corps Markdown.
  2. Télécharger les coverschaque cover distante est récupérée (fetch, redirect: 'follow') et écrite dans public/wp-content/uploads/2026/08/24/ ; le champ cover est réécrit en URL locale.
  3. Rendre le HTMLmarked.parse(body_md) produit body_html, stocké en base à côté du Markdown source.
  4. Générer le SQLcatégories, auteur unique (Alex), jeux, tags puis articles + liaisons article_tags sont sérialisés dans seed.sql.

Le téléchargement d'image et la réécriture de l'URL, au cœur du script :

for (const a of articles) {
  if (a.cover && /^https?:\/\//.test(a.cover)) {
    const filename = `${a.slug}-${a.category}${extOf(a.cover)}`;
    const local = await download(a.cover, filename);
    if (local) { a.cover = local; }
  }
  a.og_image = a.og_image || a.cover;
}

Chaque valeur est échappée pour SQLite (q(v) double les apostrophes ; qbool convertit les booléens). Puis on charge le seed dans la D1 locale :

# Génère site/seed.sql à partir de contents/**/*.md
node scripts/import-content.mjs
# Charge le seed dans la base D1 locale
npx wrangler d1 execute blogstarter-db --local --file=./seed.sql

Résultat consigné par le script : 30 articles, 10 jeux, 50 tags, un auteur (Alex).

6.5 — Routes SSR + cache edge

Trois routes couvrent tout le site, plus une 404 :

RouteFichierRôle
/src/pages/index.astroHome : spotlight, jeux couverts, derniers guides/news, tendances, newsletter
/[category]src/pages/[category]/index.astroArchive : en-tête de hub, grille + pub in-feed, pagination
/[category]/[slug]src/pages/[category]/[slug].astroArticle : hero 2 colonnes, prose + sommaire, verdict/pros-cons, ancre pub

Les routes dynamiques valident leurs paramètres et retombent proprement sur la 404 via Astro.rewrite('/404') :

const { category } = Astro.params;
if (!category || !CATEGORIES.includes(category as any)) return Astro.rewrite('/404');
const cat = await getCategory(DB, category);
if (!cat) return Astro.rewrite('/404');

Chaque page pose le même en-tête de cache edge : servi 5 min depuis le cache Cloudflare, et jusqu'à 10 min de plus en stale-while-revalidate pendant la régénération. C'est le levier « vitesse = marge par visiteur » : le SSR ne tourne qu'une fois par fenêtre, le reste est servi à froid par l'edge.

Astro.response.headers.set('Cache-Control', 'public, s-maxage=300, stale-while-revalidate=600');

6.6 — Médias sur R2

Les covers d'articles sont servies en statique (copiées dans public/wp-content/…, déployées via ASSETS). Les créatives publicitaires, elles, vivent dans le bucket R2 blogstarter-media (clés ads/…webp) et sont servies par une route dédiée src/pages/media/[...key].ts, qui lit le binding MEDIA, choisit le Content-Type par extension et pose un cache immuable d'un an :

export const GET: APIRoute = async ({ params }) => {
  const key = params.key;
  if (!key) return new Response('Not found', { status: 404 });
  const obj = await (env as any).MEDIA.get(key);
  if (!obj) return new Response('Not found', { status: 404 });
  const ext = key.split('.').pop()?.toLowerCase() || '';
  const ct = obj.httpMetadata?.contentType || TYPES[ext] || 'application/octet-stream';
  return new Response(obj.body, {
    headers: { 'Content-Type': ct, 'Cache-Control': 'public, max-age=31536000, immutable' },
  });
};

Les composants AdLeaderboard (728×90) et AdRectangle (300×250) pointent ces clés via /media/ads/…webp — détaillé en Partie 08.

Piège — redémarrer astro dev après un binding

Les bindings locaux sont chargés par platformProxy au démarrage du serveur. Si tu ajoutes un binding (ex. le bucket R2 MEDIA) dans wrangler.jsonc pendant que astro dev tourne, il ne sera pas vu. Il faut astro dev stop puis relancer pour qu'il soit pris en compte.

À ce stade, l'app tourne : le HTML du DS est devenu des composants Astro, le contenu est en D1, les médias sur R2, les routes sont en SSR avec cache edge. Les deux parties suivantes exploitent cette base : le SEO/GEO (head, JSON-LD, endpoints dynamiques) puis la monétisation.
