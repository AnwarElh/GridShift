Déploiement Cloudflare

De l'app Astro locale à un site en production sur le réseau edge de Cloudflare. La procédure réelle, dans l'ordre exact : authentification, création des ressources distantes (D1, KV, R2), application des migrations et du seed, upload des créatives, build SSR et déploiement. Puis les vérifications prod et le post-déploiement.

Le projet est prêt : composants Astro fidèles au design system, contenu importé en local dans D1, routes SSR et endpoints SEO en place. Il reste à reproduire l'infrastructure en distant (les ressources Cloudflare que le Worker consommera) puis à publier. Tout se fait avec wrangler, en s'appuyant sur le wrangler.jsonc déjà écrit lors de la Partie 06.

Rappel des bindings

Le Worker déclare quatre liaisons : ASSETS (statiques dist/), DB (D1 blogstarter-db), MEDIA (R2 blogstarter-media) et SESSION (KV, sessions Astro). Chaque ressource distante doit exister avant le déploiement, et son identifiant doit figurer dans wrangler.jsonc.

Sécurité & complétude

Aucun secret n'est requis à ce stade : le projet n'utilise aucune clé d'API (pas d'AdSense côté serveur, pas de service tiers authentifié). Le cas échéant, les secrets n'iraient pas dans wrangler.jsonc (versionné) mais dans .dev.vars en local (git-ignoré, voir Partie 10) et via npx wrangler secret put NOM en production — jamais en clair dans la config. À prévoir également : les headers de sécurité ne sont pas encore posés (voir la vérif post-deploy plus bas).

Procédure de déploiement

  1. S'authentifier auprès de CloudflareConnexion interactive (elle ouvre le navigateur, côté utilisateur), puis vérification du compte actif. 
    npx wrangler login
npx wrangler whoami   # confirme le compte you@example.com
  2. Vérifier l'adapter : imageService en passthroughDans astro.config.mjs, l'adapter Cloudflare est réglé sur imageService:'passthrough'. C'est ce qui évite d'avoir à provisionner et binder Cloudflare Images au déploiement — les images sont servies telles quelles (elles sont déjà optimisées en amont). 
    adapter: cloudflare({
  platformProxy: { enabled: true },
  imageService: 'passthrough',
})
  3. Vérifier les compatibility_flags de wrangler.jsoncLe wrangler.jsonc déclare compatibility_flags: ["global_fetch_strictly_public"]. Ce flag force les fetch() sortants du Worker à passer par le réseau public (au lieu d'un routage interne au réseau Cloudflare) — utile quand le Worker refetch ses propres ressources par URL absolue (covers, médias) pour un comportement identique à l'extérieur. Il doit rester présent tel quel au déploiement. 
    "compatibility_date": "2024-xx-xx",
"compatibility_flags": ["global_fetch_strictly_public"]
  4. Créer la base D1 distanteLa commande renvoie un database_id. Il faut le coller dans wrangler.jsonc (il remplace le placeholder utilisé en local). 
    npx wrangler d1 create blogstarter-db
# → database_id = 
    "d1_databases": [{
  "binding": "DB",
  "database_name": "blogstarter-db",
  "database_id": "",
  "migrations_dir": "migrations"
}]
  5. Créer (ou récupérer) le namespace KV SESSIONLe binding SESSION est requis par les sessions d'Astro. Ici la création a renvoyé « already exists » : on liste alors les namespaces pour récupérer l'id existant et le placer dans wrangler.jsonc. 
    npx wrangler kv namespace create SESSION   # → « already exists »
npx wrangler kv namespace list            # → id = 
    "kv_namespaces": [{
  "binding": "SESSION",
  "id": ""
}]
  6. Créer le bucket R2Bucket pour les médias (créatives pub). La commande peut poser un prompt interactif (« add on your behalf? ») qui n'est pas confirmé en contexte non-interactif : on vérifie donc l'existence du bucket juste après. 
    npx wrangler r2 bucket create blogstarter-media
npx wrangler r2 bucket list   # vérifie que blogstarter-media est bien présent
  7. Appliquer les migrations sur la D1 distanteRejoue en --remote les migrations Drizzle générées en Partie 06 (celles déjà appliquées en --local). 
    npx wrangler d1 migrations apply blogstarter-db --remote
  8. Charger le seed (30 articles) en distantExécute le seed.sql généré par le script d'import sur la base distante, puis vérifie le nombre de lignes. 
    npx wrangler d1 execute blogstarter-db --remote --file=./seed.sql
npx wrangler d1 execute blogstarter-db --remote --command "SELECT COUNT(*) FROM articles;"
  9. Uploader les créatives sur R2 (--remote)Chaque créative WebP (déjà optimisée et sans métadonnées) est poussée sous la clé ads/… attendue par les composants pub. Une commande par fichier. 
    npx wrangler r2 object put blogstarter-media/ads/arknights-endfield-728x90.webp \
  --file=media-src/ads/arknights-endfield-728x90.webp --remote
# … idem pour la seconde créative
  10. Builder l'app en SSR CloudflareProduit le bundle Worker + les statiques dans dist/ (servis via le binding ASSETS). 
    npm run build
  11. DéployerPublie le Worker et connecte tous les bindings. La sortie donne l'URL de production. 
    npx wrangler deploy

Le site est en ligne à l'adresse https://blogstarter.votre-compte.workers.dev. Les quatre bindings sont connectés et les statiques du dossier public/ (dont wp-content/) sont déployés automatiquement avec le Worker.

Coût

Pour un blog qui démarre, l'ensemble tient dans les quotas gratuits de Cloudflare (Workers, D1, R2, KV) : coût 0 €.

Vérifications post-déploiement

On sonde chaque route clé en production et on vérifie qu'elle répond bien 200 (et 404 pour un slug inexistant). Le pattern curl -o /dev/null -w '%{http_code}' n'imprime que le code HTTP.

# pages HTML
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/reviews/where-winds-meet
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/guides
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/privacy
# média R2 (attendu : image/webp) et cover statique
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/media/ads/arknights-endfield-728x90.webp
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/wp-content/uploads/2026/08/24/cover.jpg
# endpoints SEO
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/sitemap.xml
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/robots.txt
# slug inexistant → doit renvoyer 404
curl -o /dev/null -w '%{http_code}\n' https://blogstarter.votre-compte.workers.dev/guides/ce-slug-nexiste-pas
Checklist de vérif prod

Toutes ces URLs répondent 200 : /, /reviews/where-winds-meet, /guides, /media/ads/…webp (Content-Type image/webp), /wp-content/…jpg, /sitemap.xml, /robots.txt, /privacy. Un slug inexistant renvoie bien 404.

Contrôle des headers de sécurité

Au-delà des codes HTTP, on inspecte les en-têtes de réponse avec curl -I (requête HEAD). C'est le moment de constater ce qui est présent et ce qui manque.

curl -I https://blogstarter.votre-compte.workers.dev/
# on cherche : Content-Security-Policy, X-Content-Type-Options: nosniff,
# Strict-Transport-Security (HSTS), X-Frame-Options / Referrer-Policy
Headers de sécurité — à prévoir

À ce stade, aucun header de sécurité n'est encore posé par le Worker : ni Content-Security-Policy, ni X-Content-Type-Options: nosniff, ni Strict-Transport-Security (HSTS). Ils devront être ajoutés — soit via un middleware Astro qui enrichit les réponses, soit via une Transform Rule Cloudflare une fois le domaine votreblog.com branché. À noter : une CSP devra whitelister les domaines AdSense avant activation de la pub.

Pièges du déploiement

imageService passthrough

Sans imageService:'passthrough', l'adapter Cloudflare active le service d'images et exige un binding IMAGES au deploy — ressource non provisionnée ici. Le passthrough sert les images sans traitement (elles sont déjà optimisées en amont).

Binding KV SESSION requis

Astro attend un namespace KV lié à SESSION pour ses sessions. Il doit exister et son id doit être dans wrangler.jsonc, sinon le deploy échoue. La création peut renvoyer « already exists » : dans ce cas on récupère l'id via kv namespace list.

Prompt interactif R2

wrangler r2 bucket create peut afficher un prompt « add on your behalf? » qui n'est pas confirmé automatiquement en contexte non-interactif. Toujours vérifier ensuite avec wrangler r2 bucket list que le bucket a bien été créé.

Domaine & post-déploiement

Le site tourne sur le sous-domaine *.workers.dev. Il reste quelques branchements pour le mettre pleinement en production :

  1. Brancher le domaine votreblog.comDashboard Cloudflare → Worker blogstarter → Custom domain → ajouter votreblog.com. Le certificat SSL est provisionné automatiquement.
  2. Search Console + sitemapAjouter la propriété dans Google Search Console et soumettre https://votreblog.com/sitemap.xml (généré dynamiquement depuis D1).
  3. Compléter ads.txt & les pages légalesRenseigner l'identifiant AdSense réel dans ads.txt (placeholder posé en Partie 07) et remplir les [ ] restants des pages légales (Legal notice, Privacy, Cookies) — à faire valider par un juriste.
