Le Design System — commencer par ça

La fondation. Rien ne se construit tant qu'il n'est pas validé. On explique pourquoi il passe avant tout, on pose le parti pris « Command HUD », on cite les vrais tokens de styles-v2.css, on dresse l'inventaire priorisé des composants, et on fixe les bonnes pratiques qui garantissent la cohérence.

2.1 — Pourquoi démarrer par le design system

C'est l'étape la plus contre-intuitive et pourtant la plus rentable. La tentation naturelle est de « faire une première page » puis d'en dériver les suivantes en recopiant le HTML. C'est un piège.

Le piège du HTML recopié

Recopier le HTML d'une page à l'autre crée une dette de cohérence immédiate : le même bouton finit avec trois paddings différents, la même carte avec deux bordures, et chaque correction doit être répétée manuellement partout. À dix pages, c'est ingérable. Le site devient incohérent visuellement — exactement ce qui trahit un « site fait à la va-vite » aux yeux du visiteur et des régies publicitaires.

La bonne approche inverse la logique : on construit d'abord un système — un fichier CSS unique de tokens et de composants — et chaque page n'est plus qu'un assemblage de ces briques. Bénéfices concrets :

  • Cohérence garantie. Un bouton est le bouton, partout. Une carte est la carte.
  • Zéro dette de recopie. On modifie une fois, à un seul endroit, et tout le site suit.
  • Source de vérité unique. styles-v2.css est la référence. Toute évolution passe par lui.
La règle d'or (répétée dans toute la doc)

Modifier une page = modifier d'abord le design system, puis laisser la modification se répercuter. Jamais un style « en dur » dans une page. Cette discipline est ce qui rend le passage à Astro (partie 06) fidèle au pixel : le CSS validé y est copié tel quel.

2.2 — Concept & direction artistique : « Command HUD »

Un design system a besoin d'un parti pris. Sans direction forte, on retombe sur du générique — et le générique ne se retient pas.

La leçon de la V1

Une première version a été produite puis rejetée : trop « SaaS sombre générique » — coins arrondis, palette safe violet + cyan. Rien de faux, mais rien de mémorable. La leçon retenue : il faut un parti pris fort et assumé, quitte à polariser.

La V2 : Command HUD

La V2 assume une esthétique HUD / esport — l'interface d'un jeu compétitif. Ses marqueurs :

  • Fond dark quasi-noir (--bg #07080b), gris froids.
  • Un seul accent signature : le volt #03A9F4 (vert acide). Discipline mono-accent stricte.
  • Des formes angulaires : coins entaillés (clip-path « notch »), crochets de viseur (brackets), rayons quasi nuls.
  • Une grille blueprint en fond, fondue vers le haut de page.
  • Une typo à trois voix : Chakra Petch (titres, techy), Inter (lecture) et JetBrains Mono (labels système).
Pourquoi ça marche pour ce site

Le vocabulaire visuel (HUD, viseur, blueprint, mono technique) parle à l'audience gaming compétitive et distingue instantanément BlogStarter d'un blog générique. Le parti pris devient un actif de marque.

2.3 — Les tokens

Tous les tokens vivent dans le :root de styles-v2.css : surfaces, accent volt, sémantiques de statut, échelle tier S→D, typo, espacements, rayons quasi nuls. Voici un extrait fidèle des valeurs réelles.

/* Surfaces — gris froids, quasi-noir */
--bg:            #07080b;
--surface-1:     #0e1116;
--surface-2:     #141821;
--border:        #232a38;

/* Signature — VOLT (vert acide) : accent UNIQUE */
--volt:        #03A9F4;
--volt-tint:   rgba(3, 169, 244, .11);
--grad-volt:   linear-gradient(120deg, #4fc3f7, #03A9F4 55%, #0288d1);

/* Sémantiques (statut, PAS marque) */
--success: #34d399;  --warning: #ffb020;
--danger:  #ff4d6d;  --info:    #38bdf8;

/* Échelle tier list */
--tier-s: #ff4d6d;  --tier-a: #ffb020;  --tier-b: #03A9F4;

/* Typographie — trois voix */
--font-display: "Chakra Petch", system-ui, sans-serif;
--font-sans:    "Inter", system-ui, sans-serif;
--font-mono:    "JetBrains Mono", ui-monospace, monospace;

/* Rayons — angulaires (peu arrondis) + notch signature */
--r-sm: 2px; --r-md: 4px; --r-lg: 6px;
--notch: 12px;

Les formes signature

Au-delà des tokens de couleur, le système définit des utilitaires de forme qui portent l'identité HUD :

ÉlémentRéalisationEffet
Notch (.hud)clip-path: polygon(...) avec coins entaillés, double couche pour dessiner le bordLe panneau angulaire caractéristique.

La matrice d'états

Le CSS ne définit pas que des « composants au repos » : il porte l'ensemble de leurs états d'interaction. Chaque élément interactif est spécifié pour six états, ce qui garantit un feedback cohérent partout et évite les boutons ou champs « morts » visuellement.

ÉtatDéclencheurTraitement visuel
defaultAu reposSurface + bordure de base, texte pleine lisibilité.
hoverSurvol sourisBordure volt / élévation légère, transition courte (120–180 ms).
focusNavigation clavierContour focus visible (accent volt) — jamais supprimé, exigence a11y.
activeClic / appui en coursEnfoncement (teinte accentuée, léger décalage).
disabledAction indisponibleOpacité réduite, curseur bloqué, pas de hover.
errorValidation échouéeBordure/label --danger, message associé (champs de formulaire).

Responsive & breakpoints

Le système est pensé mobile-first et déclenche ses réagencements à une série de points de rupture explicites : 940 / 900 / 820 / 680 / 560 / 520 px. Aux largeurs intermédiaires, la sidebar est réorganisée (remontée ou passée sous le contenu principal selon la page), et les grilles utilitaires .grid.cols-N réduisent leur nombre de colonnes jusqu'à passer sur une seule colonne aux plus petites tailles. Aucun composant n'est redessiné : ce sont les mêmes briques, réorganisées.

2.4 — L'inventaire des composants

Le design system n'est pas qu'une palette : c'est une bibliothèque complète de composants, organisée par familles et priorisée. Chaque composant existe comme spécimen dans la page styleguide (référencé SYS.nn). Priorités : 🟢 Essentiel · 🟡 Recommandé · ⚪ Optionnel.

2.5 — La page styleguide navigable

Tous ces tokens et composants sont réunis dans une page unique : design/design-system-v2.html. Elle sert de vitrine et de contrat visuel.

design/
├── styles-v2.css          # SOURCE DE VÉRITÉ (tokens + composants)
└── design-system-v2.html  # styleguide navigable (sommaire latéral + scrollspy)

Sa structure :

  • Un sommaire latéral groupé par familles : Fondations · Navigation · Accueil & hubs · Composants UI · Gaming · Éditorial · Monétisation · États & overlays.
  • Un scrollspy qui surligne la section en cours à la lecture.
  • Chaque section montre le spécimen réel du composant, numéroté SYS.01 → SYS.45.
Point de validation obligatoire

Le styleguide doit être validé avant d'aller plus loin. C'est le dernier moment pour ajuster le parti pris à moindre coût. Une fois validé, il devient intangible : les gabarits (partie 03) puis l'app Astro (partie 06) n'en sont que des assemblages.

2.6 — Bonnes pratiques

  1. Discipline mono-accentUn seul accent de marque, le volt #03A9F4. Les couleurs sémantiques (success, warning, danger, info) servent le statut, jamais la marque. Cette contrainte est ce qui donne au site son identité tranchée.
  2. Un seul CSS sourcestyles-v2.css est unique. Aucun style « en dur » dans une page. En partie 06, ce fichier est copié tel quel dans l'app Astro et importé une seule fois dans le BaseLayout — la fidélité vient de là.
  3. Formes signature systématiquesNotch (coins entaillés), crochets de viseur, grille blueprint, rayons quasi nuls : réutiliser les utilitaires du système plutôt que réinventer des variantes.
  4. Lisibilité éditorialeInter pour le corps, largeur de prose maîtrisée (~680–720px), rythme vertical régulier. Le HUD habille, il ne gêne jamais la lecture — c'est du contenu long qu'on monétise.
  5. AccessibilitéContrastes suffisants sur fond quasi-noir, focus visibles sur les champs, transitions courtes (120–180 ms) non tape-à-l'œil, sémantique HTML propre.
Nuance accessibilité — contrastes

Le corps de texte (Inter sur fond quasi-noir) est conforme WCAG AA. En revanche, les tons les plus atténués — --text-faint et --text-dim — passent sous le seuil AA de contraste. Ils sont donc réservés aux labels non essentiels (numéros d'index mono, méta décoratives, séparateurs) et ne doivent jamais porter d'information critique ni de texte de lecture.

C'est la fondation

Tout le reste du site repose sur cette partie. Un design system solide, cohérent et validé rend les étapes suivantes rapides et fiables : les gabarits s'assemblent sans friction, l'adaptation Astro est fidèle, et la monétisation (emplacements réservés dès le CSS) hérite d'un bon CLS gratuitement. Investir ici, c'est ne pas reconstruire deux fois.
